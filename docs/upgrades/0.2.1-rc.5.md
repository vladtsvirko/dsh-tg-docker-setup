> Generated by the upstream watch task on 2026-11-03; decisions recorded the
> same day, release `0.2.1-rc.5-0.0.0` cut on this plan. Regenerate; do not hand-tune
> the findings. The procedure lives in [`../UPSTREAM-WATCH.md`](../UPSTREAM-WATCH.md).

> current release: the product part has since moved (see
> [`../VERSIONS.md`](../VERSIONS.md)). Treat every version below as the plan's
> snapshot, not as something to copy into a release.

## 3. Compatibility findings

**Verdict: no contract break for this setup.** The upgrade is mechanical; the
release work is version bookkeeping and UAT, not code migration.

| Check | Result |
|---|---|
| `@deepseek-ai/dsh` CLI `lib/` | byte-identical (`diff -rq`: only `package.json`) |
| `dsh-agent`, `dsh-llm`, `dsh-session` (connector's peer imports) | byte-identical |
| `dsh-plugin-manager`, `dsh-app-boot` (gates `dsh plugin add` / `allow-version` / peer check) | byte-identical |
| `dsh-base`, `dsh-headless`, `dsh-acp-app`, `dsh-client-ui-cordis` | byte-identical |
| Published packages with changed content | **24 of 294** shipped packages |
| Connector peer range `>=0.1.0-rc.6 <0.3.0-0` vs `0.2.1-rc.5` | satisfied; the loader evaluates with `includePrerelease: true`, so **no `allow-version` exemption is needed** |
| Penpot plugin peer `dsh-tools >=0.1.0-rc.6 <0.3.0-0` | satisfied |
| Profile config we write (`provider`, `model`, `botToken`, penpot block) | no removed or renamed keys |
| `dsh --version` output format (entrypoint parses it) | unchanged (`0.2.1-rc.5`) |
| New client plugin `ui-entry-customization` delivery | ships inside the `dsh-web-app` bundle, which resolves from the image, so an existing profile picks it up on rebuild; no profile reset needed |

The 24 changed packages are the client UI (`ui-conversation`, `ui-sidebar`,
`ui-sidebar-right`, `ui-chat`, `ui-workspace`, `ui-plugin-manager`,
`ui-agent-preset`, `settings-*`, `product-analytics`, `cot-translation`,
`client-modules`), the built web frontend, `llm-deepseek`,
`llm-deepseek-api-key`, `llm-deepseek-account`, `mcp-client`, `mcp-resources`,
`web-app`, `api-session-controller` (comment only), `api-remotes`,
`cordis-client-runner` (descriptions), `tool-cordis` (generated type catalog),
`agent-preset` (shipped skill reference text).

Residual risks, all non-blocking:

- **Model route drift** (`deepseek-official` only): the pinned `DSH_MODEL` is not
  a listed id, so it passes through untouched, but the picker now mirrors
  DeepSeek's published list, and a listed model whose `min_version` exceeds the
  runtime is refused with `CLIENT_UPGRADE_REQUIRED`. Our default route is
  `opencode-go`, which is untouched.
- **UI-only churn**: the web UI changes shape (More menus, pins, thinking blocks).
  Nothing in Telegram depends on it, but UAT should still look at `/web`.
- **Release mechanics, not code**: a new DSH part means a new product line
  (`0.0.0`), a matching connector tag, and the
  `--i-know-versions-are-incompatible` gate on both update paths.

## 4. Upgrade plan

Order matters: the connector tag must exist before the setup image builds,
because the entrypoint resolves `#v${DSH_SETUP_VERSION}` at boot.

1. **Connector** — `dsh-telegram-connector`
   1. Bump `devDependencies` for `dsh-agent`, `dsh-llm`, `dsh-session` to
      `0.2.1-rc.5`; leave the peer ranges alone (they already admit rc.5).
   2. `pnpm install && pnpm typecheck && pnpm test`; fix anything the new
      client typings surface (expected: nothing, the peer libs are identical).
   3. Add a `COMPATIBILITY.md` row: `0.2.1-rc.5-0.0.0 | 0.2.1-rc.5 | tested`,
      and move the previous row to `previous`.
   4. Commit, tag `v0.2.1-rc.5-0.0.0`, push.
2. **Setup** — `dsh-tg-docker-setup`
   1. `Dockerfile`: `ARG DSH_VERSION=0.2.1-rc.5`,
      `ARG DSH_SETUP_VERSION=0.2.1-rc.5-0.0.0`.
   2. `VERSION` → `0.2.1-rc.5-0.0.0`; every image tag in `compose.yaml`; the
      version example in `AGENTS.md`.
   3. Docs: compatibility notes in `README.md`, `docs/VERSIONS.md`,
      `docs/UPGRADE.md` (the "current line" examples), UAT baseline tag.
   4. `node --test *.test.mjs`, `bash -n entrypoint.sh install.sh update.sh
      healthcheck.sh`, and `docker compose config` in a throwaway checkout
      (`cp .env.example .env`) — never against a deployed `.env`.
   5. `docker compose build dsh` on the build host, then boot it once against a
      scratch `data/` to prove `dsh --profile web` starts and the connector
      mounts without an exemption.
   6. Commit, tag `v0.2.1-rc.5-0.0.0`, push; CI checks the tag pair.
3. **Deployment**
   1. Host: `./update.sh --self-check` — expect *no compatible tag* plus the new
      tag in the list. Then either
      `./update.sh --self --i-know-versions-are-incompatible` (takes the newest
      tag) or `./update.sh --self-to v0.2.1-rc.5-0.0.0` (explicit target;
      `--self-to` takes no flag — it already trusts its caller).
      From Telegram: `/system update all --i-know-versions-are-incompatible`.
   2. The image rebuilds, the connector reinstalls at the new ref, the trial
      card appears — **Commit** only after the checks below.
4. **Post-upgrade checks**
   - `/about` → connector `0.2.1-rc.5-0.0.0`, runtime `0.2.1-rc.5`, peer range
     unchanged; no exemption is needed, so none should be granted.
   - `/system status`, one real prompt in a topic, and the mirror in `/web`
     (new More menus and pinned entries visible in the sidebar).
   - Resume an old session (rc.2-era log) and confirm it still streams.
   - Model picker lists `deepseek-v4.1-flash` under `opencode-go`, and one
     completion succeeds.
5. **Rollback** — nothing new: the supervisor trial restores the previous
   checkout, image and profile. Keep `dsh-backend:0.2.1-rc.2-0.8.0` until the
   commit.

## 5. Decisions (resolved 2026-11-03)

### D1. Take `0.2.1-rc.5` now, or wait for the `0.2.2` RC line? — **take rc.5**

The release pair is going out on this line: connector and setup re-tagged as
`0.2.1-rc.5-0.0.0`. The `0.2.2` line (worktrees, plugin-management overhaul,
`subagent_oar`, i18n) is the next alignment, not a reason to skip this one.

### D2. Model route: follow DeepSeek's published listing — **follow, but only show
what the deployment can call**

Follow the published listing (so a model DeepSeek ships later appears without a
release), with one product constraint: **a model the deployment cannot actually
use is not offered.** That already holds in the runtime and is not something the
setup has to implement:

- a provider appears only once it has a usable credential — a pi-ai route whose
  `apiKeyEnv` resolves to nothing reports an empty catalog, and the built-in
  `deepseek-official` route hides itself without a saved key;
- our entrypoint registers the chosen pi-ai provider only when its key variable
  is non-empty, so an unconfigured route never reaches the picker;
- a listed model gated by `client_requirements` is refused before network I/O
  (`CLIENT_UPGRADE_REQUIRED`), not silently attempted.

Recorded as an acceptance check instead of code: see the UAT list. The `models`
override stays available as the opt-out for a deployment that must freeze its
catalog.

### D3. `engines.dsh` / peer-range policy — **withdrawn**

Not a decision: the version line (`<dsh>-<product>`) already states the DSH
release each tag was built for, and the loader's peer check is a separate
mechanical gate that rc.5 satisfies without an exemption. No change to the
connector manifest.

- More menus: pin a plugin launcher, reload, confirm the pin survives.
